# 03 · 失效条件

每条机制在什么条件下**不再成立**、坏的时候**长什么样**、怎么最早发现。
这一节比「怎么用」更重要：这套东西的失败几乎全是静默的。

## A. 网络层

| 机制 | 失效条件 | 表现 | 发现 |
| --- | --- | --- | --- |
| ssh 隧道（`nanny_beat` / `act` / `report` / `shift_guard`） | 隧道主机换了、ssh 密钥不在、主机 22 口不通 | `TUNNEL_SPAWN_FAIL` / `TUNNEL_DIED_EARLY`；之后每次 `CALL_FAIL` / `LOOK_FAIL` | `nanny_beat.log` 里连续 `*_FAIL` |
| 隧道端口借用 | `LPORT` 上已经有一个**别人的**监听（不是到 `api.yuyuworld.app` 的隧道） | `TUNNEL_ADOPT existing`，然后所有调用 HTTP/TLS 报错或返回怪东西 | 看到 `ADOPT` 但紧接着 `CALL_FAIL`，就 `netstat -ano \| findstr 18443` 手工看是谁 |
| `heart.js` 的出网 | 它走 **Node 的 https 直连**，不走我们的隧道（见下框） | `tick 出错: ECONNRESET / timeout`；`state.json` 的 `lastAt` 停住 | 日志里连续 `tick 出错` |
| DNS / IPv6 | 本机 IPv6 不稳 | 间歇超时 | `nanny_beat.py` 已把 `getaddrinfo` 强制成 `AF_INET`；`heart.js` 没有 |

> **一个没完全解释清楚的差异（照实记）**：同一台机器上，python `urllib` / `curl` / 裸 TLS
> 直连 `api.yuyuworld.app` 的失败率是 40%～100%，所以我们给 python 这条腿加了 ssh 隧道；
> 而 `heart.js` 用 Node 的 https 直连一直是通的。机制未查明（代理对两者的处理不同）。
> **失效条件**：如果哪天 `heart.log` 开始连续 `tick 出错`，第一件事是先用一小段 node
> `https.get('https://api.yuyuworld.app/v1/profile')` 验证直连还通不通，再决定要不
> 要把 `heart.js` 也改成走隧道——别在没验证前先改代码。

## B. 密钥层

| 机制 | 失效条件 | 表现 | 发现 |
| --- | --- | --- | --- |
| 操作密钥 `FISH_WORLD_KEY` | 过期/被换/复制错 | `401/403 密钥无效`；`heart.js` 启动即 `缺 FISH_WORLD_KEY` 退出 | 日志原文；`apiGet` 里 401/403 单独抛错 |
| 密钥来源 | 环境变量和 ZCode MCP 配置**两份不一致** | 一半调用通、一半 401 | 只看一处来源：env 优先，其次 MCP 配置 |
| 观看密钥 | 隧道主机上那个 600 文件路径写错 / 变量名不是 `FISH_WORLD_WATCH_KEY` | `grep` 出空 → `Bearer ` 空 token → 401 → `JSON.parse` 抛错 | `watch.log` 的 `LOOK_FAIL`；手工 ssh 跑同一条命令 |
| 观看密钥外泄面 | 有人把它写进日志/聊天/仓库 | 世界规则层面的风险，不会报错 | 代码里命令只有 `$K`；`env.example` 只有变量名 |

## C. 唤醒层（最容易假绿的一层）

| 机制 | 失效条件 | 表现 | 发现 |
| --- | --- | --- | --- |
| 唤醒目标 | 会话改名 / 归档 / 换机器，且自解析也失败（`network.db` 路径不对） | **`sendRN` 退出码 0，日志「唤醒 N 条」全绿，会话一次不醒** | 第 2 层证据（会话里有没有那条消息）；`heart.log` 启动行里的「目标 xxx」 |
| `sendRN` 的成功判据 | RN 对 refused 也返回 0 | `ok=true` 但没人收到 | 同上：只认「会话里出现了」 |
| RN daemon | daemon 没起 / 二进制路径不对 | `spawn` error → `ok=false` → 自动降级 fyi，事件不丢 | `heart.log` 的 `唤醒失败:` |
| 每日额度 | `maxWakePerDay` 设小 / 当天真的很多事 | 之后全部降级 fyi，人会感觉「今天没人叫我」 | 日志 `fyi N 条（今日额度用完）` |
| `tune.enabled=false` | 手工暂停后忘了开 | 只保活，不处理事件 | 日志 `已暂停（tune.enabled=false）` |
| 指纹 FIFO 200 | 一天事件 > 200 且服务端还在重播极老的事件 | 极老事件被当新事件再叫一次 | 概率低；真要查就把 `seen` 调大 |
| 定时激活 | `heart.js` 进程活着但 `tick` 卡住（例如 `apiGet` 卡满 15s 超时 × 连续失败） | `lastActivate` 不前进 | `state.json` 的 `lastActivate` 与当前时间差 > 2× 间隔 |

## D. 世界侧规则（不是 bug，但会让「看起来该动」变成没动）

| 机制 | 失效条件 | 表现 |
| --- | --- | --- |
| 保活 | `KEEPALIVE_MS` > 10 分钟 → 发呆；> 1 小时 → 下线 | 别人看你是「发呆/离线」，消息不推送 |
| 定时激活 | 她正在睡觉 / 在自己家里做事 | 叫醒了 agent 也叫不动身体；别把「没动」当故障 |
| 好友申请 | 只能**当面**发；她在家时进不去 | `her.json.reachable=false`，只能等 `★LEFT_HOME` |
| 长 `sleep` | 她的会话 `sleep` 期间，外部推送断不了 `wait`（引擎只认 `kind=user`） | 叫不醒 → 对策是从一开始就不让她用长 sleep 等时间 |
| 沉默静音 | 平台插件的 `quietHours` 连**真事件**一起静音 | 夜里事件只投递不响 |

## E. Windows / 启动层

| 机制 | 失效条件 | 表现 | 发现 |
| --- | --- | --- | --- |
| `.bat` 行尾 | UTF-8 + LF + 中文注释 | cmd 按 GBK 嚼碎，rc=255，从建好起就没工作过 | `file` / 十六进制看行尾；本仓强制 CRLF |
| 无窗启动 | 用 `-WindowStyle Hidden` / `start /min` 防闪 | 控制台先被创建再被隐藏，Win11 交给 Windows Terminal 托管，照样闪 + 抢焦点 | 事件钩子实测（轮询 0.15s 会漏 0.4s 的窗） |
| VBS 判活 | 用 `heart.lock` 的 mtime 判「过期」 | 永远判过期 → 起第二个实例 → 抢锁/双跑 | 改成扫 `node.exe` 的 `CommandLine` |
| 手工起的进程 | 直接 `node heart.js` 但没带 env | 状态目录落到 `__dirname/state`（可接受）或读不到密钥（退出） | 启动日志里的 `FISH_HEART_HOME` 与目标 |
| `pythonw` vs `python` | 用 `python.exe` 起常驻 | 控制台窗口 | 入口一律 `pythonw` / `wscript` |

## F. 短命工具

| 工具 | 失效条件 | 表现 |
| --- | --- | --- |
| `shift_guard.py` | 世界把「班上有活」的文案改了 → `parse_tasks` 正则不中 | 一直 `ON_DUTY_NO_TASK`，不处理活 |
| `shift_guard.py` | 活必须 10 分钟内处理；电脑睡了 / 进程没起 | 漏活（扣钱），日志里没有 `TASK_OK` |

| `act.py` | 每次调用都 `initialize` 一遍 | 慢（两跳），但换来零状态 |

## G. 观测本身的失效条件

- **日志是 append-only 不切分**：按 `HH:MM` 全文正则 grep 会命中几十天前的旧段。
  读当天三步：先 `grep -n "=== ... start"` 取最后一条定锚 → 只读锚之后 → 再上正则。
- **`her.json` 30 分钟过期**：`heart.js` 会显示「她的状态没读到」，这是设计，不是坏了。
- **`doing` 不反映动作**：她那边会话的 `doing` 字段不会随着一次工具调用变化，
  判「叫醒了有没有真干活」只认会话里的 tool 调用 / turn。
- **`polls` 计数**：进程活着不等于在轮询；看 `lastAt` 与 `lastErr`，不要看 pid。
