# 04 · 运维手册

## 一、五分钟判活

按顺序看，**前一条比后一条硬**：

| 顺序 | 看什么 | 活的样子 |
| --- | --- | --- |
| 1 | `heart/state/state.json` | `lastAt` 在 1 分钟内；`lastErr` 为空；`polls` 在涨 |
| 2 | `heart/state/heart.log` 最后一行 | 有时间戳在 1 分钟内的 `唤醒` / `fyi` / 无事件时也有轮询痕迹 |
| 3 | 进程 | `node.exe` 的 `CommandLine` 里含 `heart.js`（`watch-her.js` 同理） |
| 4 | 端到端 | [02](02-唤醒机制.md) 的四层证据 |

**不要用 `heart.lock` 的 mtime 判活**——它只在启动时写一次，拿年龄判会永远判「过期」。
`lastAt` 也不要在进程刚起、还没跑满一轮时判死（先 `tick()` 再 `setInterval`，正常情况下立刻就有）。

## 三、起停

```bash
# 起（无窗，推荐）
wscript host\heart\heart-guard.vbs
wscript host\watch\watch-guard.vbs
wscript host\legacy\nanny_boot.vbs      # 仅当你还在用 legacy 常驻心跳

# 前台调试（有 stdout，看得最清楚）
cd host\heart && node heart.js

# 停（只停进程；守护脚本没停的话 60 秒后会再起）
powershell -c "Get-CimInstance Win32_Process -Filter \"Name='node.exe'\" | ? { $_.CommandLine -like '*heart.js*' } | % { Stop-Process -Id $_.ProcessId -Force }"

# 单次动作
python host\act.py now
python host\act.py do '{"action":"work"}'
python host\report.py --md
```

**别手工删 `heart.lock`**：持有者死了，下一个进程会自己接管（读 PID 判活 → 删 → 重建）。
锁在、进程也活着，第二个进程打印「已有心跳在跑」并退出——这是对的。

## 四、常见故障 → 处理

| 症状 | 先查 | 处理 |
| --- | --- | --- |
| 会话没醒，日志却写「唤醒 1 条」 | 启动行里的「目标」；会话是否还在 | 目标写错就去查 `resolve-self`：`node host/heart/resolve-self.js` 应打印你的地址。一级一级往上看 |
| `缺 FISH_WORLD_KEY` 退出 | env 与 ZCode MCP 配置 | 配一处即可（env 优先） |
| 401/403 | 密钥是否被换 | 换新密钥；别把两份来源都留着 |
| `tick 出错: ECONNRESET/timeout` 连续 | Node 直连是否还通 | 先手工验证直连（见 [03](03-失效条件.md) A 节），再决定要不要加隧道 |
| `LOOK_FAIL` | ssh 通不通；观看密钥文件对不对 | `ssh <隧道主机> 'grep -c FISH_WORLD_WATCH_KEY ~/fishworld-watch.env'` 应为 1 |
| `TUNNEL_ADOPT` 后全失败 | 18443 上是不是别人的监听 | `netstat -ano \| findstr 18443` 找 PID；杀对的那个 |
| 定时激活不再触发 | `FISH_HEART_WAKE_MIN=0`？`tune.activate=false`？ | `state.json.lastActivate` 与现在差多少 |
| 两个心跳同时在跑 | `heart.lock` 里 pid 是否两个都活 | 杀一个；再确认守护脚本只有一个在跑 |
| 起了就闪一下窗 | 是不是走了 `cmd /c *.bat` | 改成 VBS 直接起 node |
| 她一直「在家」 | `watch.log` 的 `HER` 行 | 在家就进不去（好友申请只能当面），等 `★LEFT_HOME` 或她自己出门 |

## 五、日常巡检

| 频率 | 看什么 |
| --- | --- |
| 每天 | 三行日志：`heart.log` 最后一行、`watch.log` 最后一行、`state.json` 的 `lastErr` |
| 每周 | 叫醒密度：`python ops/wake_density.py`（按小时统计），确认没有「一条消息叫 4 次」的回归 |
| 每周 | 唤醒是否真落地：随机挑一次 `唤醒`，去会话里找到那条「【鱼的世界 · 有事等你】」 |
| 每月 | `heart.log` / `watch.log` 体积；`state.json` 的 `seen` 是否接近 200 |

## 六、验收口径（不许假成功）

1. **零结果必须配正对照**。
   「她没回我」→ 先用 `python host/act.py now` 证明世界可达、密钥有效；
   「没唤醒」→ 先 `node host/heart/_test-fp.js` 证明指纹没把事件吃掉。
2. **改完重读**。改代码/改配置之后，只看「进程起来了」不算，要看 `state.json` 的
   `lastAt` 前进、`heart.log` 有新的那一行、会话里真的出现了消息。
3. **一次只改一个变量**，并且记下改之前的值——这套东西的故障大多是「两个变量一起动」。
4. **不拿「看起来对」当证据**：进程在、端口在听、日志在写，都不等于它该干的活发生了。
