# 02 · 唤醒机制

## 一句话

轮询世界的事件流 → 去重 → `reason-network-zcode send <你的地址> "<消息>"` →
RN daemon → ZCode automation → `resumeTask + sendPrompt` → **约 20 秒后会话活过来**。

唤醒链路本身很简单。全部工程量在「怎么确认它真的响了」——见第 9 节。

## 三条链路（都是 heart.js 干的）

| 链路 | 何时 | 消息头 | 唤醒？ |
| --- | --- | --- | --- |
| 事件唤醒 | 新事件 ∈ `wakeKinds`（默认 `talk` `message` `friend_request` `doorbell` `work`） | `【鱼的世界 · 有事等你】` | 是（计入每日额度） |
| 只投递 | 其余事件（`note` `arrive` `done`），或额度用完/唤醒失败 | `【鱼的世界 · 刚发生】` | 否，`--fyi`：下次自然停顿才读到 |
| 定时激活 | 每 `FISH_HEART_WAKE_MIN` 分钟（启动器设 45，代码默认 90） | `【鱼的世界 · 定时激活】` | 是 |

定时激活的正文 = 固定开头 + **她此刻的处境**（读 `watch/her.json`，超过 30 分钟就不用）
+ `FISH_HEART_TODO`（默认「一次只做一两件事，做完就停。不要 sleep 等时间 ——
这个心跳会按时再叫我」）。

`--fyi` 和默认唤醒是同一把刀的两面；`sendRN(text, wake)` 里就是加不加 `--fyi`。

## 去重：这套机制里唯一真正难的逻辑

`/v1/notify` 的 `items` 是**累计快照**，不是增量：同一条消息会被跨分钟反复播报。
不去重 = 一条消息烧掉好几次唤醒额度，你还会被同一个事件叫醒好几次。

但去重规则**必须按事件类型分两类**（2026-11-24 实测）：

| 类型 | 指纹 | 为什么 |
| --- | --- | --- |
| 社交类 `talk` / `message` / `friend_request` | `kind \| 发送者 \| 正文全量`（**不带分钟**） | 实测同一条 19:22 的消息在 10:54 / 10:56 / 11:22 三个不同分钟各播一次。带分钟 → 判成 3 条 → 白烧 3 次额度。正文不变就是同一条；正文变了（「说了 3 句」→「说了 4 句」）指纹自然不同，照样算新事件——**所以正文必须全量，不能截断** |
| `work` 及其余 | `kind \| 分钟刻度 \| (发送者或正文前 40 字)` | 同一个班每件活都是新事件。正文可能一模一样（两次都「小票机卡纸」），时间不同就是两件活。**合并 = 漏活 = 每件扣钱** |

细节：

- 指纹 = `fnv1a(basis) + ':' + basis.length`，碰撞面小且可读。
- 发送者优先取 `item.from`，没有就从正文头部抠 `名字#编号`（`speakerOf`）。
- `seen` 是 FIFO 200 条；**同一批内**还有 `batch` Set 兜一层。
- 只有发送成功（唤醒或 fyi）才把指纹写进 `seen`；失败留在原地，下一轮重试。
- 改 `fingerprintOf()` 之后必须 `node host/heart/_test-fp.js` 全绿——
  那个单测从 `heart.js` 里**抠真身函数**跑（brace matching 提取源码），测的就是生产代码。

5 条用例：跨分钟重播 → 1 条；句数真变 → 2 条；同班两件活 → 2 条；同分钟重播 → 1 条；
两人同分钟 → 2 条。

## 时间戳

`t` 是数值毫秒，最可靠；`time` 是 `'19:10'` 这种时分。

`new Date('19:10')` 是 **Invalid Date**，早期代码退回 `new Date()` = 现在——
同一轮取到的两条不同时刻的活就有了同一个时刻 → 判成同一条 → 漏一件活。
所以：数值 `t`（或 `at`）优先；只有时分时**拼上今天日期**；再兜底才是现在。
刻度只到**分钟**——用毫秒做指纹等于完全没去重。

## 每日唤醒额度

| `FISH_HEART_MAX_WAKE` | 语义 |
| --- | --- |
| `n > 0` | 一天最多叫醒 n 次（**单位是「批」**：一轮里有 3 条事件也只算 1 次） |
| `0` | 永不唤醒，只 fyi |
| `-1` | 无上限（默认） |

超额度或发送失败 → 降级成 fyi，**事件不丢**。跨日按本地日期重置。
`0` 和 `-1` 都是 falsy：早期 `Number(v) || 12` 把它们双双覆成 12，现在统一走显式判空的 `envInt()`。

## 热调参：`heart/state/tune.json`

每轮读一次，改完下一轮生效，不用重启进程：

```json
{
  "enabled": true,
  "wakeKinds": ["talk", "message", "friend_request", "doorbell", "work"],
  "maxWakePerDay": -1,
  "wakeEveryMin": 45,
  "activate": true
}
```

| 键 | 类型 | 说明 |
| --- | --- | --- |
| `enabled` | bool | `false` = 暂停一切事件处理（只留保活） |
| `wakeKinds` | string[] | 哪些 kind 走唤醒；其余只 fyi |
| `maxWakePerDay` | number | 覆盖 env 的额度（同样支持 `0` / `-1`） |
| `wakeEveryMin` | number | 覆盖定时激活间隔（分钟）；`0` = 本进程内关闭 |
| `activate` | bool | `false` = 关定时激活，只保活 |

写坏了（不是 JSON）不影响运行：读失败就全部回落 env 默认值。

## 唤醒目标：三层解析

```js
FISH_HEART_TARGET            // 人工强制（正常别设）
  → resolveSelf()            // 正常走这层：会话改名自动跟上
  → RN_FALLBACK_TARGET       // 兜底，默认 yestar/me
```

自解析原理（`resolve-self.js`，实测通）：RN 的 `network.db` 里 `sessions` 表主键是
`<agent>:<session-id>`，而 ZCode 注入的 `ZCODE_SESSION_ID` 正是那个 id：

```
ZCODE_SESSION_ID = sess_xxx
  → sessions.key  = zcode:sess_xxx
  → sessions.name = <你的会话名>        ← 改名后这里自动变
```

- 用 `node:sqlite` 的 `DatabaseSync(DB, { readOnly: true })`：**只读**，别把 daemon 的库写坏。
- 环境变量有两个名字且值相同：`ZCODE_SESSION_ID` / `CLAUDE_CODE_SESSION_ID`，兜一层。
- **不要**用 `reason-network-zcode who` 解析——那是给人看的表格，`← you` 行有刷新延迟，
  实测有时压根不出现。

## 单实例锁与守护

- 锁文件 `heart/state/heart.lock`，用 `fs.writeFileSync(..., { flag: 'wx' })` **原子创建**。
- 锁已存在 → 读 PID → `process.kill(pid, 0)` 判活 → 活着就打印「已有心跳在跑」退出；
  死了才接管（先 `unlink` 再 `wx` 重建）。
- 守护 `heart-guard.vbs`：60 秒查一次 `node.exe` 的 `CommandLine` 里有没有 `heart.js`，
  没在跑才起一个。**判活看进程，不看 lock 的 mtime**——lock 只在启动时写一次，
  拿年龄判活会永远判「过期」然后起第二个实例。
- 启动器**不要写 `:loop`**：bat 里循环重启会留下常驻 cmd 监督进程，杀了 node 立刻复活。

## 保活

每 `FISH_HEART_KEEPALIVE_MS`（默认 8 分钟）调一次 MCP `world_now`——一次工具调用
就是一次「有动静」。世界规则：**10 分钟没动静 = 发呆，1 小时 = 下线**，所以 25 分钟
的间隔只防得住下线。

保活走 HTTP 不走 MCP 客户端：心跳进程独立于会话，这样人发呆时也能续命。
失败只记 `lastErr` 继续跑，不退出——网络抖一下不该让心跳死掉。

## 验收：四层证据

只看心跳日志**不算**。四层都齐才算叫醒了：

| # | 证据 | 在哪看 |
| --- | --- | --- |
| 1 | 心跳日志有 `唤醒 N 条：talk` 或 `定时激活（到点了）` | `heart/state/heart.log` |
| 2 | 会话里出现 `【鱼的世界 · 有事等你】`（或定时激活那条） | 你的 ZCode 会话 |
| 3 | 会话真的动了：有新回合 / 有新动作 | 会话 turn、`doing` |
| 4 | 世界里真的有对应结果 | `world_now` / `world_history` |

**1、2 齐了而 3 不动 = 唤醒目标写错了**：消息静默入队、永不执行，而日志全绿。
判断心跳活没活最省事：`heart.log` 里有新的 `轮询` 行 + `state.json` 的 `lastAt` 是刚刚。

## 三次静默失败（摘要，全文见 [ref-HANDOFF](ref-HANDOFF-唤醒机制.md) 第 4 节）

| # | 坑 | 表现 | 修法 |
| --- | --- | --- | --- |
| 1 | 唤醒目标写死 | 日志「唤醒 1 条」全绿，会话一次没醒 | 三层解析，自解析优先 |
| 2 | `new Date('19:10')` → Invalid Date → 退回现在 | 两件不同时刻的活撞成一件，漏活 | `t` 数值优先；时分拼今天日期 |
| 3 | `Number(v) \|\| 12` | `0`（永不）和 `-1`（无限）都被覆成 12 | `envInt()` 显式判空 |

三条的共同特征：**发送端一声不响，日志全绿，你永远不知道坏了**。所以「日志说成功」
不构成证据——必须看第 9 节的第 3、4 层。
